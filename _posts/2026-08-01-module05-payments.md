모듈 5는 약 3개월간 진행한 프로젝트의 마지막 단계였다.
앞선 모듈에서 장바구니, 결제, 크레딧, AI 구독권, 토스페이먼츠 연동, 멱등성 처리와 모니터링까지 구현했기 때문에 이번에는 새로운 기능을 추가하기보다 **기존 결제 시스템을 실제 서비스에서 안정적으로 운영할 수 있는 수준으로 개선하는 것**에 집중했다.

특히 결제 시스템은 단순히 요청이 정상적으로 처리되는 것만으로는 부족하다고 생각했다.

사용자가 동시에 여러 결제를 요청하거나, 네트워크 문제로 동일한 요청이 반복되거나, 외부 결제는 성공했지만 내부 데이터 반영이 실패할 수도 있다. 또한 서비스가 운영되면서 결제 데이터가 계속 증가하면 기존에는 문제가 없던 조회 방식도 성능 저하의 원인이 될 수 있다.

그래서 모듈 5에서는 크게 다음 세 가지를 목표로 리팩토링과 성능 개선을 진행했다.

* 결제 정합성 및 동시성 제어 강화
* 데이터 증가를 고려한 결제 조회 성능 최적화
* 장애를 감지하고 복구할 수 있는 운영 구조 구축

## 결제 트랜잭션 원자성 강화

첫 번째로 점검한 부분은 **결제 과정에서 일부 작업만 성공하는 상황**이었다.

결제는 하나의 데이터만 변경하는 작업이 아니다. 사용자의 크레딧을 차감하고, 주문과 결제 데이터를 생성하며, 최종적으로 구매한 강의나 구독권의 권한까지 반영해야 한다.

예를 들어 다음과 같은 상황이 발생할 수 있다.

```text
크레딧 차감 성공
→ 주문 생성 성공
→ 결제 저장 성공
→ 강의 권한 반영 실패
```

이 경우 사용자의 크레딧은 차감됐지만 실제 강의를 이용할 수 없는 데이터 불일치가 발생한다.

이를 방지하기 위해 크레딧 차감부터 주문·결제·권한 반영까지 **하나의 트랜잭션 단위로 처리**하도록 구조를 다시 정리했다.

중간 과정에서 하나라도 실패하면 전체 작업을 롤백하여 일부 데이터만 반영되는 부분 성공 상태가 발생하지 않도록 했다.

이를 통해 결제 결과와 실제 서비스 데이터의 상태가 일치하도록 만들고 **결제 데이터의 정합성을 강화**했다.

## 비관적 락을 통한 동시 결제 제어

트랜잭션만 적용한다고 해서 모든 문제가 해결되는 것은 아니었다.

특히 크레딧 차감이나 구독 갱신처럼 **동일한 데이터를 여러 요청이 동시에 변경하는 상황**에서는 경쟁 상태가 발생할 수 있다.

예를 들어 사용자의 크레딧이 10,000원 남아 있는 상태에서 7,000원짜리 결제 요청 두 개가 거의 동시에 들어온다고 가정했다.

```text
요청 A → 잔액 10,000원 확인
요청 B → 잔액 10,000원 확인

요청 A → 7,000원 차감
요청 B → 7,000원 차감
```

두 요청이 모두 기존 잔액을 기준으로 결제를 진행하면 실제 잔액보다 많은 금액이 사용되는 문제가 발생할 수 있다.

이를 방지하기 위해 크레딧 차감과 구독 갱신 과정에 **비관적 락(Pessimistic Lock)**을 적용했다.

먼저 데이터를 변경하는 요청이 해당 행을 잠그고 처리를 완료한 이후 다음 요청이 접근하도록 했다. 또한 락을 획득한 이후 현재 상태를 다시 검증하도록 구성했다.

이를 통해 다음과 같은 문제를 방지할 수 있었다.

* 잔액 초과 차감
* 동일 구독 중복 갱신
* 동시에 발생한 결제 요청 간 상태 충돌
* 동일 데이터에 대한 중복 처리

결제 시스템에서는 처리 속도보다 금액과 권한 데이터가 정확하게 유지되는 것이 우선이라고 판단했다.

## 멱등성 기반 중복 결제 방어 강화

모듈 4에서는 `Idempotency-Key`를 이용해 동일한 결제 요청이 반복되더라도 실제 결제가 한 번만 처리되도록 구현했다.

모듈 5에서는 이 구조를 다시 점검하면서 **동일 요청이 거의 동시에 들어오는 상황까지 방어할 수 있도록 보완**했다.

전체적인 흐름은 다음과 같다.

```text
사용자 결제 요청
        ↓
Idempotency-Key 확인
        ↓
기존 요청 여부 확인
        ↓
fingerprint 비교
        ↓
결제 처리
        ↓
결과 저장 및 재사용
```

같은 사용자와 같은 멱등성 키로 요청이 들어오면 새로운 결제를 만들지 않고 기존 결과를 재사용한다.

반대로 같은 키를 사용했지만 구매 유형이나 강의, 구독 플랜 등 요청 내용이 다르면 fingerprint가 달라지기 때문에 충돌 요청으로 처리한다.

이 구조를 통해 사용자의 중복 클릭이나 네트워크 재전송이 발생하더라도 **실제 결제는 한 번만 수행되도록 보장**했다.

## DB UNIQUE 제약을 통한 이중 방어

애플리케이션에서 중복 여부를 검사하더라도 두 요청이 거의 동시에 검증 로직을 통과하는 경쟁 상태가 발생할 수 있다.

따라서 애플리케이션 레벨의 검증만으로 결제 데이터의 중복을 완전히 방지하기 어렵다고 판단했다.

그래서 결제, 멱등성, 활성 구독 등 중복 데이터가 발생하면 안 되는 영역에 **DB UNIQUE 제약을 함께 적용**했다.

```text
Application Validation
        ↓
Business Logic
        ↓
DB UNIQUE Constraint
```

애플리케이션에서 먼저 중복 요청을 확인하고, 최종적으로 데이터베이스에서 동일한 데이터가 저장되는 것을 한 번 더 차단한다.

즉, 애플리케이션과 데이터베이스의 **이중 방어 구조**를 통해 경쟁 상태에서도 중복 결제 데이터가 생성되지 않도록 했다.

## 외부 결제 장애 복구 구조 개선

외부 결제 시스템을 연동하면서 내부 트랜잭션만으로 해결할 수 없는 문제도 있었다.

대표적인 경우가 다음과 같다.

```text
토스 결제 승인 성공
        ↓
내부 DB 반영 실패
```

외부 결제가 이미 승인된 이후 내부 DB에서 오류가 발생한다고 해서 외부 결제까지 자동으로 롤백되는 것은 아니다.

결국 사용자는 실제 돈을 결제했지만 내부 크레딧이나 결제 상태는 반영되지 않는 상황이 발생할 수 있다.

이를 해결하기 위해 **외부 승인과 내부 반영을 분리하고 내부 반영 실패 건을 복구할 수 있는 구조**를 적용했다.

```text
외부 결제 승인
      ↓
내부 데이터 반영
      ↓
실패 여부 확인
   ↙       ↘
성공       실패
            ↓
       복구 대상 등록
            ↓
        배치 재처리
```

내부 반영에 실패한 결제 건은 복구 대상으로 남겨두고, 이후 배치가 해당 데이터를 다시 확인하여 내부 반영을 재시도하도록 했다.

이를 통해 장애가 발생하더라도 외부 결제와 내부 데이터가 계속 불일치한 상태로 남는 것을 방지했다.

결제 시스템에서는 장애 자체를 완전히 없애는 것뿐만 아니라 **장애 발생 후 정상 상태로 돌아갈 수 있는 구조를 만드는 것**도 중요하다는 점을 확인할 수 있었다.

## N+1 문제 제거

모듈 5에서는 데이터가 증가했을 때의 조회 성능도 점검했다.

대표적으로 장바구니와 수강 여부를 확인하는 과정에서 동일한 종류의 조회가 반복되는 구조가 있었다.

예를 들어 강의 목록을 가져온 뒤 각각의 강의에 대해 장바구니 여부를 다시 조회하면 데이터 수만큼 추가 쿼리가 발생한다.

```text
강의 목록 조회 1회
+
각 강의의 장바구니 여부 조회 N회
```

데이터가 적을 때는 문제가 크지 않지만 강의와 사용자가 증가할수록 DB 요청도 함께 증가하게 된다.

이를 개선하기 위해 필요한 ID를 먼저 수집하고 **일괄 조회(Bulk Query)**한 뒤 애플리케이션에서 결과를 매핑하도록 변경했다.

```text
강의 목록 조회
      ↓
필요 ID 일괄 수집
      ↓
Bulk Query
      ↓
조회 결과 매핑
```

장바구니 20건을 기준으로 확인했을 때 기존에는 **41회의 조회가 발생했지만 개선 후 3회로 감소**했다.

약 **93%의 쿼리를 감소**시킨 것이다.

또한 수강 여부 조회 역시 강의별로 반복 조회하지 않고 필요한 정보를 한 번에 조회하도록 변경했다.

## 불필요한 세션 조회 제거

강의 조회 과정에서 사용자 정보를 확인하기 위해 세션을 추가로 조회하는 부분도 있었다.

하지만 인증 과정에서 이미 필요한 사용자 정보를 확보할 수 있었기 때문에 동일한 정보를 다시 조회하는 것은 불필요한 DB 접근이라고 판단했다.

그래서 인증된 사용자 정보를 활용하도록 조회 구조를 변경했다.

이를 통해 강의 목록을 조회할 때 발생하던 추가적인 세션 조회를 제거하고 **불필요한 DB 접근을 최소화**했다.

## 장바구니 변경·삭제 Bulk Query 적용

장바구니에서 여러 강의를 선택하거나 삭제할 때도 기존에는 각 데이터마다 개별적으로 처리하는 구조가 있었다.

예를 들어 100개의 장바구니 항목을 삭제한다면 개별 처리 방식에서는 최대 100번의 삭제 요청이 발생할 수 있다.

이를 Bulk Query 기반으로 변경했다.

```text
기존
Item 1 → DELETE
Item 2 → DELETE
Item 3 → DELETE
...
Item 100 → DELETE

개선
Items [1...100] → Bulk DELETE
```

이를 통해 다건 변경·삭제 작업을 **100회에서 1회 수준으로 줄일 수 있었고**, 동일한 항목 수를 처리할 때 발생하는 DB 호출을 크게 감소시켰다.

## 결제 내역 페이지네이션 적용

결제 내역은 서비스가 운영될수록 계속 증가하는 데이터다.

초기에는 데이터가 많지 않기 때문에 전체 데이터를 조회해도 문제가 없지만, 결제 데이터가 수천 건, 수만 건으로 증가하면 한 번에 모든 데이터를 조회하는 방식은 DB와 서버 모두에 부담이 된다.

그래서 결제 내역 조회에 **페이지네이션(Pagination)**을 적용하고 한 번에 조회하는 데이터의 수를 제한했다.

초기 운영 기준으로 최대 **100건 단위**로 데이터를 처리하도록 구성했다.

이를 통해 전체 결제 내역을 한 번에 메모리에 적재하지 않고 필요한 범위만 조회할 수 있도록 했다.

## 구독 갱신 Keyset 처리

구독 자동 갱신 역시 데이터 증가를 고려해야 했다.

구독자가 많아질 경우 모든 갱신 대상 데이터를 한 번에 조회해서 처리하면 메모리 사용량과 DB 부하가 증가할 수 있다.

그래서 구독 갱신 대상을 **100건 단위의 Keyset 방식으로 나누어 처리**하도록 변경했다.

```text
갱신 대상 조회
      ↓
100건 처리
      ↓
마지막 ID 기준 다음 100건 조회
      ↓
반복
```

Offset 기반 페이지네이션과 달리 이전 데이터의 위치를 계속 계산하지 않고 마지막으로 처리한 데이터의 키를 기준으로 다음 데이터를 조회한다.

이를 통해 구독 데이터가 증가하더라도 일정한 처리 단위로 갱신할 수 있도록 했다.

100건은 초기 운영을 고려해 설정한 보수적인 기본값이며, 실제 트래픽과 처리시간에 따라 조정할 수 있도록 구성했다.

## 구독별 독립 트랜잭션 적용

구독 자동 갱신 과정에서는 하나의 구독에서 문제가 발생했을 때 다른 구독까지 영향을 받지 않도록 하는 것도 중요했다.

예를 들어 100명의 구독을 하나의 트랜잭션에서 처리하다가 50번째 구독에서 오류가 발생하면 앞에서 정상 처리된 구독까지 롤백될 수 있다.

이를 방지하기 위해 **구독별로 독립된 트랜잭션을 적용**했다.

```text
구독 A → 독립 트랜잭션
구독 B → 독립 트랜잭션
구독 C → 독립 트랜잭션
...
```

하나의 구독 갱신이 실패하더라도 해당 구독만 실패하도록 영향 범위를 제한했다.

이를 통해 대량 구독 갱신 과정에서 일부 장애가 전체 작업으로 확산되는 것을 방지했다.

## 인덱스와 메트릭을 통한 운영 대응

성능 개선과 함께 문제가 발생했을 때 원인을 추적할 수 있도록 조회 조건에 맞는 **복합 인덱스**를 구성하고 운영 메트릭과 감사 로그도 보완했다.

특히 결제와 구독은 문제가 발생했을 때 단순히 실패 여부만 확인해서는 원인을 찾기 어렵다.

그래서 다음과 같은 정보를 추적할 수 있도록 했다.

* 결제 처리 결과
* 중복 요청 여부
* 멱등성 충돌
* 구독 갱신 결과
* 외부 결제와 내부 데이터 불일치
* 복구 처리 결과
* 주요 결제 성능 지표

이를 통해 장애가 발생했을 때 어떤 요청에서 문제가 발생했는지 확인하고, 장애의 영향 범위를 추적할 수 있도록 했다.

## 모듈 5에서 구축한 결제 시스템

모듈 3부터 모듈 5까지 결제 시스템은 단계적으로 발전했다.

모듈 3에서는 장바구니와 크레딧을 기반으로 **기본적인 결제 흐름을 구현**했다.

모듈 4에서는 토스페이먼츠, 구독권, 멱등성, 장애 복구와 모니터링을 추가하면서 **운영 가능한 결제 구조로 확장**했다.

마지막 모듈 5에서는 기존 기능을 다시 점검하면서 실제 서비스 운영에서 발생할 수 있는 문제에 대응하는 데 집중했다.

최종적으로 결제 시스템을 다음 다섯 가지 관점에서 정리할 수 있었다.

### 정합성

트랜잭션과 DB 제약을 통해 결제 과정에서 데이터가 서로 다른 상태로 남는 것을 방지했다.

### 안정성

멱등성과 비관적 락을 통해 중복 결제와 동시에 발생하는 결제 요청을 제어했다.

### 성능

N+1 제거, Bulk Query, 페이지네이션, Keyset 처리를 통해 데이터 증가에 따른 DB 부하를 줄였다.

### 운영 대응

인덱스, 메트릭, 감사 로그를 통해 결제 장애를 감지하고 문제 발생 지점을 추적할 수 있도록 했다.

### 확장성

Processor 분리와 설정 기반 처리 단위 관리를 통해 결제 유형이나 데이터가 증가하더라도 기존 구조를 크게 변경하지 않고 확장할 수 있도록 했다.

## 모듈 5에서 배운 점

모듈 5를 진행하면서 가장 크게 느낀 점은 **기능이 정상적으로 동작하는 것과 실제로 운영할 수 있는 시스템을 만드는 것은 다르다**는 것이었다.

처음에는 결제가 성공하고 데이터가 저장되면 기능 구현이 끝났다고 생각하기 쉬웠다.

하지만 실제 운영 상황을 생각하면 더 많은 경우를 고려해야 했다.

* 같은 결제 요청이 동시에 들어오면 어떻게 할 것인가
* 크레딧을 동시에 사용하면 잔액을 어떻게 보호할 것인가
* 외부 결제는 성공했는데 내부 처리가 실패하면 어떻게 복구할 것인가
* 데이터가 100건에서 10,000건으로 증가해도 같은 구조를 사용할 수 있는가
* 한 사용자의 구독 갱신 실패가 다른 사용자에게 영향을 주지는 않는가
* 장애가 발생했을 때 어디서 문제가 발생했는지 확인할 수 있는가

이런 문제를 하나씩 해결하면서 백엔드 개발에서는 정상적인 흐름뿐만 아니라 **실패하는 상황과 데이터가 증가하는 상황까지 함께 설계해야 한다는 것**을 배울 수 있었다.

특히 트랜잭션, 락, 멱등성, DB 제약, 배치, 페이지네이션과 같은 기술이 각각 독립적인 기술이 아니라 **하나의 서비스를 안정적으로 운영하기 위해 서로 보완하는 요소**라는 점을 직접 경험할 수 있었다.

## 마무리

약 3개월 동안 진행한 프로젝트에서 결제 시스템은 단순한 크레딧 결제 기능에서 시작했다.

이후 외부 결제 연동과 구독 시스템을 추가하고, 중복 결제 방어와 장애 복구 구조를 구축했으며, 마지막으로 동시성 제어와 조회 성능까지 개선했다.

특히 모듈 5에서는 새로운 기능을 많이 추가하기보다 기존 시스템을 다시 살펴보면서 **정합성, 안정성, 성능, 운영 대응, 확장성**이라는 관점에서 부족한 부분을 보완했다.

결과적으로 트랜잭션과 DB 제약으로 데이터 불일치를 방지하고, 멱등성과 비관적 락으로 중복 및 동시 결제를 제어했으며, N+1 제거와 Bulk Query, 페이지네이션, Keyset 처리를 통해 데이터 증가에 대비했다.

또한 장애가 발생하더라도 메트릭과 로그를 통해 문제를 추적하고 복구할 수 있는 구조를 갖추면서 **실제 상용 서비스를 고려한 결제 시스템의 기반을 구축**할 수 있었다.

이번 프로젝트를 통해 백엔드에서의 리팩토링은 단순히 코드를 깔끔하게 만드는 작업이 아니라, **서비스가 커지고 예상하지 못한 문제가 발생하더라도 안정적으로 동작할 수 있도록 구조를 개선하는 과정**이라는 것을 배울 수 있었다.
